01 / framework

A repeatable interview loop

The interviewer is evaluating your reasoning, not your ability to list every AWS product.

Clarifyusers, features, SLO
EstimateRPS, storage, growth
Drawrequest + data path
Stressfailure + hot keys
Operatealerts + rollback

Ask first

Read versus write ratio? Peak or average? Global or regional? Strong or eventual consistency? Data retention? RTO/RPO? Compliance? Budget? Multi-tenant isolation?

State assumptions

“I will design for 10k RPS peak, p99 under 300 ms, three AZs, one-hour RTO and no data loss for committed writes.” Assumptions make trade-offs reviewable.

Quick drill

What is a weak answer to “design a URL shortener”?

Starting with “use DynamoDB and API Gateway” without clarifying traffic, redirect latency, custom aliases, expiration, abuse controls, analytics and availability.

02 / edge and entry

Make the front door boring

Global entry should absorb traffic, enforce policy and route to healthy regional capacity.

Route 53DNS / health checks
CloudFrontcache / edge
WAF / Shieldpolicy / DDoS
ALB / API GWHTTP / APIs
Serviceprivate compute

Route 53 versus Global Accelerator

Route 53 answers DNS routing and health policy. Global Accelerator uses static anycast IPs and AWS network paths. Choose based on failover speed, client constraints and protocol.

CloudFront is not only CDN

Use it for cache, TLS termination, edge controls, origin shielding and reduced origin load. Do not cache personalized or sensitive content without explicit policy.

       → CloudFront + WAF

03 / compute

Choose by workload shape

Compute choice follows control needs, runtime duration, startup time, concurrency and operational ownership.

NeedDefault candidateTrade-off
HTTP service, managed scaleECS Fargate or App RunnerLess node work; less low-level control.
Complex platform / custom schedulingEKSPowerful; cluster and add-on ownership.
Short event-driven workLambdaFast scale; duration, concurrency and cold-start limits.
Stable high utilizationEC2 Auto ScalingControl and price; patching and capacity ownership.

Scaling signals

Scale on request rate, queue age, concurrency or latency when those represent demand. CPU is useful only when CPU is the actual bottleneck.

Backpressure

Protect dependencies with quotas, bounded queues, timeouts, circuit breakers and load shedding. Infinite retries turn a small failure into an outage.

04 / data design

Consistency is a product decision

Pick the data primitive from access patterns, correctness and failure behavior—not familiarity.

RDS / Aurora

Relational constraints and transactions. Multi-AZ improves failover; read replicas scale reads; cross-region replication is a recovery trade-off.

DynamoDB

Predictable key-value/document access at scale. Design partition keys, hot-key behavior, capacity mode, TTL and conditional writes.

ElastiCache

Reduce read latency and origin load. Define invalidation, stampede protection, eviction and behavior when cache is empty.

S3

Durable object storage for blobs and data lake patterns. Use versioning, lifecycle, encryption, replication and access policies.

Quick drill

When does a read replica not solve a consistency problem?

When a read must immediately observe a committed write. Replication lag means the read path needs primary reads, version tokens, quorum logic or an explicit eventual-consistency contract.
Data model before database brand5 / 13

05 / async patterns

Decouple time and failure

Queues turn bursty work into controlled work. They do not remove failure; they make failure measurable and recoverable.

APIvalidate + accept
SQSbuffer + retry
Workerbounded concurrency
DLQpoison messages
EventBridgefan-out policy

At-least-once reality

Consumers must be idempotent. Use a stable event ID, deduplication strategy, visibility timeout, retry budget and dead-letter policy.

Streaming choice

SNS, SQS and EventBridge solve different routing needs. Kinesis and MSK fit ordered/high-volume streams with explicit partition and consumer semantics.

Pattern
API → SQS → worker → database
              ↘ failures → DLQ → replay workflow

06 / high availability and DR

AZ failure is not region failure

Say exactly which failure your architecture survives and which recovery process handles the next one.

PatternUse whenCost / risk
Multi-AZSurvive a local infrastructure failure.Regional control plane and regional dependencies remain a boundary.
Backup and restoreRTO can be minutes or hours.Cheaper; recovery speed and restore correctness need tests.
Warm standbyNeed faster regional recovery.Secondary capacity and replication cost.
Active-activeVery low RTO and global traffic.Highest complexity: conflicts, routing, operations.

RPO

How much committed data can be lost? Synchronous Multi-AZ and asynchronous cross-region replication answer different RPOs.

RTO

How quickly must service return? DNS TTL, warm capacity, data promotion, cache warm-up and operator steps all count.

07 / security

Make access explainable

Security design should show who can do what, to which resource, through which boundary, with which evidence.

Identity

IAM roles over long-lived keys. STS for temporary access. SSO for humans. KMS for key control. Secrets Manager for rotation. Resource policies for cross-account boundaries.

Network

Private subnets for internal workloads, security groups as stateful boundaries, NACLs as subnet controls, VPC endpoints for private service access and WAF at the edge.

Detect

CloudTrail, GuardDuty, Security Hub, Config and access analysis.

Prevent

SCPs, permission boundaries, policy-as-code and deny-by-default controls.

Contain

Separate accounts, blast-radius boundaries, quarantine roles and tested break-glass access.

Prove

Audit trail, owner, review date, least privilege evidence and incident runbook.

Least privilege plus observable change8 / 13

08 / operations

Design for the on-call engineer

A system is not production-ready if operators cannot detect, explain, mitigate and recover from failure.

SLIAvailability, latency, freshness, correctness
MTTDTime until a useful alert fires
MTTRTime until user impact ends

Instrument

CloudWatch metrics and alarms, structured logs, X-Ray or OpenTelemetry traces, deployment markers and business metrics such as checkout success.

Operate

Runbooks, dashboards, escalation policy, load tests, game days, rollback automation, capacity alarms and post-incident actions with owners.

Alert on a user symptom, then preserve enough context to find the responsible boundary.

09 / LLM platform pattern

Bedrock gateway under load

For LLM systems, capacity is tokens, concurrency, quota and provider behavior—not only instance CPU.

Clientauth + tenant
Gatewayquota + routing
Bedrockmodel invocation
TelemetryTTFT / tokens
Fallbackdegrade safely

Reliability controls

Timeouts, bounded retries with jitter, circuit breakers, concurrency limits, quota-aware routing, streaming, idempotency and explicit fallback policy.

Metrics

Throttling, requests, input/output tokens, TTFT, inter-token latency, end-to-end latency, provider errors, queue age and cost per tenant.

Incident drill

Bedrock returns throttling errors and the gateway latency spikes. What is the first hidden amplifier to check?

Immediate retries. A retry storm can multiply provider calls and worsen throttling. Bound retries, add jitter, cap concurrency and use a controlled fallback or queue.

11 / interview scenarios

Trade-offs in one sentence

Practice concise decisions, then expand only where the interviewer probes.

Multi-AZ or multi-region?

“Multi-AZ is the baseline for local failure; multi-region is for regional failure and brings replication and consistency trade-offs.”

SQS or Kinesis?

“SQS fits independent work items and worker scaling; Kinesis fits ordered, partitioned streams and replayable consumers.”

RDS or DynamoDB?

“RDS fits relational constraints and flexible queries; DynamoDB fits known access patterns and horizontal scale.”

Lambda or containers?

“Lambda fits bounded event work; containers fit long-lived services, custom runtimes or stable high utilization.”

12 / close

The AWS design checklist

Before you finish, make the architecture defensible from request to recovery.

Architecture

Requirements, estimates, request flow, data model, cache, async boundaries, AZ/region strategy, consistency and security.

Operations

SLOs, dashboards, alerts, runbooks, deploy strategy, rollback, backups, restore test, quotas, cost and ownership.

A senior answer does not say “AWS is highly available.” It says which failure is covered, how traffic moves, what data can be lost, how recovery is triggered, and how the team proves it.
