01 / mental model

Design from guarantees

Start with user-visible guarantees, then choose Kubernetes and cloud primitives that make those guarantees testable.

LoadRPS, concurrency, payload
SLOAvailability, latency, errors
StateStateless or durable
FailureAZ, node, dependency
RecoveryRTO, RPO, rollback

Interview order

Clarify requirements. Estimate traffic and data. Draw request flow. Define failure boundaries. Choose primitives. Explain observability, security, cost and operations.

Platform order

Build a safe golden path: identity, networking, deployment, storage, telemetry, policy and recovery. Product teams consume it without reinventing controls.

Quick drill

A service needs 99.95% availability, p95 under 250 ms, and recovery from one AZ failure. What must your design clarify first?

Answer: traffic shape, state ownership, dependency SLOs, RTO/RPO, AZ distribution and the exact user journey covered by the SLO. Capacity comes after the contract.

02 / control plane

One API, many reconcilers

The API server is the control-plane boundary. Controllers observe state and converge it toward the desired state.

Clientkubectl / platform
API serverAuth, admission, API
etcdSource of truth
ControllersReconcile state
NodesRun workloads

Core components

kube-apiserver mediates every request. etcd stores cluster state. scheduler binds unscheduled pods. controller-manager maintains replicas and status. kubelet executes the pod contract.

EKS boundary

AWS manages the Kubernetes control plane and its availability. You still own workload behavior, node capacity, IAM, networking, add-ons, policies, data and recovery.

Control-plane conversation
client → kube-apiserver → admission → etcd
controller watch → compare desired/current → act through API
kubelet → start containers → report status through API
Controllers never need direct etcd access3 / 14

03 / workload primitives

Choose the right controller

The abstraction should match identity, lifecycle and storage semantics. A Deployment is not a universal answer.

Deployment

stateless

ReplicaSet-backed rolling replacement for APIs and workers without stable identity.

Ask

How do you prevent traffic reaching a pod before it is ready?

Use a readiness probe. A Service selects only ready endpoints; startup probes protect slow initialization.

StatefulSet

identity

Stable network identity and ordered lifecycle for workloads that require it. Storage still needs an explicit backup story.

DaemonSet

per-node

One workload per eligible node: log agent, security sensor, or node-level telemetry.

Job / CronJob

finite work

Batch completion and scheduled work. Make jobs idempotent and bound retries.

Common interview trap

“Kubernetes restarted the pod” is not the same as “the service recovered.” Verify readiness, endpoint removal, request success, latency and downstream effects.

Lifecycle semantics drive the controller4 / 14

04 / scheduling and capacity

Resources are a contract

Requests influence placement. Limits constrain execution. Autoscaling only works when signals and limits reflect reality.

Pod-level controls

requests.cpu and requests.memory shape scheduling. Limits protect a node but can cause throttling or OOMKills. Probes define availability, not capacity.

Minimal resource contract
resources:
  requests:
    cpu: 250m
    memory: 256Mi
  limits:
    cpu: "1"
    memory: 512Mi

Placement controls

Use taints/tolerations for dedicated capacity, affinity for locality, topology spread for failure-domain balance, and PodDisruptionBudgets for voluntary disruption.

Fast diagnosis
kubectl top pods -A
kubectl describe node NODE
kubectl get pods -A -o wide
Quick drill

Pods are Pending while nodes show spare CPU. What do you inspect next?

Memory, pod density, ENI/IP capacity, taints, affinity, topology constraints, PVC zone binding, quotas and scheduler events. “Spare CPU” is not proof of schedulability.
Placement is multidimensional5 / 14

06 / EKS architecture

Separate managed control from owned risk

EKS removes control-plane operations, not platform engineering. Draw the AWS boundaries explicitly.

Route 53DNS / failover
ALBIngress / WAF
EKS APIManaged control plane
NodesEC2 / Karpenter
DataRDS / S3 / queues

AWS-managed

Control-plane lifecycle, API server replicas and etcd operation. Validate endpoint access, version support, add-on compatibility and audit integration.

Team-owned

Node groups, AMIs, Karpenter, IAM, VPC CNI, load balancer controller, storage drivers, policies, workloads, quotas, observability and recovery.

Design question

Why can a healthy EKS control plane still have a production outage?

Nodes, CNI/IP capacity, load balancer targets, security groups, storage, quotas, IAM, a bad rollout or a downstream dependency can fail while the API server remains healthy.
Managed control plane ≠ managed application7 / 14

07 / storage and state

Keep state outside the blast radius

Kubernetes can run stateful workloads. It does not make databases durable, consistent or backed up by default.

EBS

Block storage, normally tied to one AZ. Use the EBS CSI driver and understand volume binding before scaling nodes across zones.

EFS

Shared filesystem semantics through the EFS CSI driver. Validate latency, throughput mode and application locking.

S3

Object storage for artifacts, backups and durable blobs. Use IAM conditions, encryption, lifecycle and replication deliberately.

RDS / Aurora

Prefer managed database primitives for critical state. Kubernetes owns connection policy and consumers, not database magic.

QuestionWhat good design saysEvidence
What if a pod dies?Replica or restart; state remains external.Recovery test and application metrics.
What if an AZ dies?Replicated data and schedulable capacity remain.AZ failure exercise, RTO/RPO.
What if data is corrupted?Point-in-time restore and tested backups.Restore drill with measured RTO.

08 / security

Identity follows the workload

Avoid shared node credentials. Give each workload only the cloud actions it needs, then make that policy reviewable.

Identity chain

Human → SSO role → Kubernetes RBAC → ServiceAccount → EKS Pod Identity or IRSA → IAM role → AWS API. Every hop needs an owner, audit trail and bounded permissions.

Useful check
kubectl auth can-i --list \
  --as=system:serviceaccount:app:api -n app

Boundary controls

RBACNetworkPolicyPod SecurityKMSSecrets ManagerCloudTrailECR scanning

Use policy-as-code in CI. Alert on wildcard permissions, public exposure, role changes and secret access anomalies.

Quick drill

A pod needs to read one S3 prefix. Would you attach an admin policy to the node role?

No. Use a workload identity role with a narrow resource ARN and prefix condition. Test access and log the role usage.
Least privilege is an architecture property9 / 14

09 / observability

Health is more than pod status

Observe the user journey, the platform and the dependency graph. A green pod can serve a broken product.

SLIWhat users experience: success, latency, freshness
SLOTarget reliability over a time window
BudgetHow much failure remains before action

Signals

Metrics: Prometheus and CloudWatch. Logs: Fluent Bit and centralized storage. Traces: OpenTelemetry. Events: Kubernetes audit and object events. Profiles: only when evidence points to CPU/runtime cost.

Alert on symptoms

Alert on availability, error rate, p95/p99 latency, queue age, restart rate, OOMKills, pending pods, node pressure, API latency and dependency failures. CPU alone is not an SLO.

Readiness answers “should this endpoint receive traffic?” Liveness answers “should this process be restarted?” Neither answers “is the user journey healthy?”
Start with SLOs, then instrument causes10 / 14

10 / delivery and reliability

Make change reversible

The safest deployment is one with a small blast radius, a clear signal and a known rollback.

Testunit / contract
Scanimage / policy
Stagesmoke / load
Canarysmall exposure
Promoteobserve / rollback

Safety controls

Immutable image tags, two-person production approval, PodDisruptionBudget, graceful shutdown, backward-compatible migrations, topology spread and automated rollback.

Scale controls

HPA for workload demand, Karpenter or Cluster Autoscaler for nodes, queue-based backpressure and explicit quotas. Test cold start and scale-up time before the event.

Deployment evidence
kubectl rollout status deployment/api -n app --timeout=120s
kubectl rollout history deployment/api -n app
kubectl rollout undo deployment/api -n app
Fast rollback beats heroic debugging11 / 14

11 / production debugging

CrashLoopBackOff is a symptom

Start from user impact, narrow the failing boundary, then inspect the previous process lifetime.

Impacterrors / latency
Scopenamespace / AZ / version
Eventsscheduler / kubelet
Previous loglast process
Fixrollback / config / capacity
Fast triage
kubectl get pods -n app
kubectl describe pod POD -n app
kubectl logs POD -n app --previous
kubectl get events -n app --sort-by=.lastTimestamp

Exit 137

Often memory pressure or OOMKilled. Check container and node memory, limit, working set and recent rollout.

Probe failure

Check startup time, endpoint semantics, dependency coupling and probe timeout. Do not use liveness as a dependency health check.

Pending

Inspect scheduler events, requests, taints, affinity, quotas, PVC topology and node/IP capacity.

Healthy but slow

Trace downstream calls, queues, connection pools, throttling, disk and network. Pod phase is not a latency metric.

12 / interview drills

Answer with trade-offs

Strong answers expose assumptions, failure behavior and validation. They do not recite product names.

One AZ is down

How does traffic move? Can pods schedule elsewhere? Is data available? What RTO is achieved?

Multi-AZ nodes and topology spread preserve capacity; Route 53/ALB removes unhealthy targets; data needs independent replication; test the exact RTO.

Pods are healthy, API is slow

What do you inspect before adding replicas?

Trace request path: load balancer, endpoints, app queues, connection pools, downstream latency, throttling, network and storage. Extra replicas can amplify a broken dependency.

How do you secure AWS access?

Describe the identity chain for one workload.

ServiceAccount mapped to a least-privilege IAM role through Pod Identity or IRSA; secrets come from a managed store; CloudTrail and policy review provide evidence.

How do you plan a peak?

What proves the cluster will handle it?

Historical load model, capacity test, quota check, warm-up time, scaling signals, dependency limits, dashboards, runbook and rollback.

13 / capstone

Design a production platform

Put the pieces together: a multi-AZ EKS platform for an internal API with bursty traffic, sensitive data and an SLO.

Route 53DNS + health
WAF / ALBedge + TLS
EKSmulti-AZ workloads
RDS / S3managed state
TelemetrySLO + audit

Must explain

Request path, identity, deployment strategy, resource requests, autoscaling, zone failure, database recovery, secret flow, alerts, quotas and cost controls.

Must test

Load, pod loss, node loss, dependency timeout, failed rollout, AZ loss, restore from backup and alert delivery. Record RTO/RPO and user impact.

Mastery test: can you identify what fails, how it is detected, how it recovers, and how you prove the recovery?
